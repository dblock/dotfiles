# Create project

Create a small, working first version. Follow the workflow below; explicit user limits override its defaults.

Prepare and validate the scaffold locally, then create the GitHub repository and open the scaffold as the first PR before implementing functionality. Include code and documentation linting in the scaffold; implementation and artwork follow in focused PRs.

Pause for user review and explicit approval after agreeing scope and design, after opening the scaffold PR, and after opening the implementation PR. Present the outcome and wait rather than automatically continuing. Incorporate requested adjustments, then wait for approval again; resume from the current phase when the user says to continue. Also obtain approval of the logo concept before creating artwork. Local-only or other explicit user limits override these gates and PR steps.

## 1. Define and agree

Ask for purpose, intended behavior, ecosystem, and project name. Default destination to `~/source` and GitHub owner to `dblock`. Agree on a small first version and a brief design before implementing: public API/CLI, dependencies, host integration, and package/workspace layout.

Check repository and registry name availability early. Distinguish repository, registry package, scope, command, and plugin names; ask before changing the name or choosing a scope. An npm `E404` can indicate an unpublished name, but authentication/network errors cannot establish availability, and lookup cannot guarantee registry acceptance. Example: [scoped npm naming without changing the repository or command](https://github.com/dblock/oxlint-plugin-spellcheck/pull/15).

When selecting runtimes, dependencies, development tools, or GitHub Actions, verify current releases and prefer the latest stable versions; do not copy stale versions from example projects or rely on remembered version numbers. Use modern supported APIs and configuration. Choose an older version only for a concrete compatibility requirement and document why; exclude prereleases unless explicitly requested. Distinguish the latest runtime used for development/CI from the minimum supported runtime, and test both when applicable.

## 2. Scaffold

Initialize the repository locally with `git init -b master`. For a new repository without a base commit, ask for authorization to create and push a minimal README-only bootstrap commit on `master` so the scaffold PR has a base. This is the sole bootstrap exception to the PR-only rule; do not proceed without explicit authorization. If authorized, commit only a project title and brief description in README, including the Copilot co-author trailer, then create the scaffold in a separate Git worktree before adding other files. Create the GitHub repository and push the bootstrap base only when the scaffold PR is ready. If authorization is declined, keep work local until the user provides a base. For an existing repository, inspect its status and worktrees without overwriting existing work. Subsequent development changes go through PRs; explicitly authorized release automation may push release and next-version commits directly as described below.

Work in a separate Git worktree for each PR, keeping the primary checkout on `master`. Name branches `<username>/<topic>`, using the GitHub login (`dblock` by default), for example `dblock/scaffold`, `dblock/implementation`, and `dblock/logo`. Create an unused sibling worktree path with `git worktree add -b <username>/<topic> <worktree-path> <base>`; use `master` or the prerequisite PR branch as the base. Inspect existing branches and worktrees first; never overwrite or remove someone else's checkout. Run edits, dependency installation, and validation in the selected worktree.

Include the worktree workflow and `<username>/<topic>` naming convention in both AGENTS and CONTRIBUTING.

Run the project's local test and lint commands before every push, including updates to an existing PR. State the actual commands and this pre-push requirement in AGENTS and CONTRIBUTING; run package validation as needed for the changes.

After PRs merge, always clean up their local topic branches and worktrees. Fetch with pruning, verify the PR's merged state through GitHub (squash/rebase merges may not appear in `git branch --merged`), and inspect each worktree for uncommitted or untracked work and dependent stacked PRs. Remove clean, no-longer-needed worktrees with `git worktree remove`, then delete their local branches. Use `git branch -D` only after verifying the PR was merged and no unmerged commits or dependent work would be lost when Git's ancestry check rejects a squash/rebase-merged branch. Prune stale worktree metadata and verify cleanup. Never delete `master`, active PR branches, or dirty worktrees; report blocked cleanup instead of discarding work. Include this post-merge cleanup rule in AGENTS and CONTRIBUTING.

Use ecosystem tooling where useful, without overwriting existing work. Add package metadata, a version, public entry point, explicit packaged-file list, and MIT license. Choose supported runtimes from dependencies and host compatibility, not copied example versions.

Include the initial documentation and separate CI workflows described below in the scaffold PR; refine them after implementation. Keep release instructions explicitly provisional until release behavior exists. Add individual test, lint, and package badges to README. Avoid redundant Gemfile declarations for dependencies already provided by `gemspec`, and use narrowly scoped lint exceptions with concrete reasons rather than blanket cop disables. Latest scaffold example: [ruby-gem-release PR #1](https://github.com/dblock/ruby-gem-release/pull/1), covering package setup, AGENTS, contributor/design/release documents, documentation linting, and separate workflows. Use it as a reference, not a version-pinned template.

Use title case for human-readable Markdown headings and YAML workflow, job, and step display names, for example `Setup and Validation` and `Run Tests`; preserve proper names, acronyms, code identifiers, expressions, and URLs. Enable capitalization checks in scaffold linting: for Ruby enable `Markdown/HeadingCapitalization` from `rubocop-prose` with `Style: title_case`; for JavaScript configure a compatible markdownlint custom heading-capitalization rule, such as `markdownlint-rule-title-case-style`, after verifying its current configuration and compatibility. For YAML display names, use a compatible lint rule or a focused YAML-aware checker integrated into the local lint command and `lint.yml`; test valid and invalid names and avoid checking machine identifiers or arbitrary `name` fields. If no suitable rule exists, implement the smallest tested checker rather than claiming syntax linting enforces capitalization. Include the convention and exact commands in AGENTS and CONTRIBUTING.

Add `.gitignore` before installing dependencies or generating artifacts. For Ruby gems, ignore `.bundle/`, `Gemfile.lock`, `.rspec_status`, `coverage/`, `pkg/`, `vendor/`, and `.ruby-lsp/`; for JavaScript packages, ignore `node_modules/`, `coverage/`, and generated package tarballs, but commit `package-lock.json`. Ignore project-specific generated files and local secrets without hiding tracked sources, fixtures, or logo assets. Preserve existing ignore rules.

Add a root `AGENTS.md` with concise, actionable instructions for automated contributors; refine it after implementation. Start with `# Working on <project>` and a direction to read CONTRIBUTING and DESIGN. Cover the project's purpose and non-goals; implementation/test locations; supported runtimes and public dependency APIs; non-obvious invariants and prohibited shortcuts; focused-test and integration-fixture expectations; exact validation commands; documentation and changelog rules; feature version bumps in the same PR (increment minor; for `0.x` reset patch to zero, e.g. `0.1.1` → `0.2.0`; for `1.x` and later preserve patch, e.g. `5.3.1` → `5.4.1`); and ask the user whether to bump major for breaking changes. Also capture Git safety (topic branches from `master`, prefer one coherent commit for most PRs, allow squash or rebase merges but not merge commits, no direct default-branch development commits/pushes, no force-push to `master`, and no merge/publication/tags without authorization). Document any explicitly authorized release-automation exception separately. Require preservation of unrelated worktree changes and single-line Markdown paragraphs. Link detailed contributor/design/release instructions rather than duplicating them, and include only rules applicable to the actual implementation, not speculative restrictions.

Capture ongoing maintenance rules, not this skill's one-time creation sequence: verify and prefer latest stable versions when selecting or updating tools while preserving supported-runtime compatibility; keep `Test`, `Lint`, and `Package` workflows separate; maintain applicable Coveralls and Ruby Danger checks; run local tests and lint before every push, and package validation before committing when applicable, including real-artifact consumer checks when packaging or public entry points change. Require changelog entries for features, improvements, and fixes (but not minor changes such as typos), with actual PR numbers and contributor attribution; require the Copilot co-author trailer and AI disclosure on behalf of `@dblock` for AI-authored PRs/comments, and closing issue references rather than manual issue closure. For feature additions, bump the package version in the same PR: increment the minor component, resetting patch to zero for `0.x` (e.g. `0.1.1` → `0.2.0`) and preserving patch for `1.x` and later (e.g. `5.3.1` → `5.4.1`). If a change is breaking, ask whether the user wants a major bump before choosing the version. Put this policy in the project's AGENTS.md. Prohibit unauthorized credential setup and overwriting published versions or release tags. Once artwork exists, link its maintenance instructions and preserve editable sources, licenses, README placement, and rendering checks.

Use concrete invariants, not generic advice: a spelling plugin might require offline dictionaries, original Unicode source offsets, and no global dependency mutation; a filesystem plugin might require read-only discovery, deterministic diagnostics, and real installed-CLI fixtures.

- Ruby: `lib/`, a version constant, gemspec, Gemfile, Rakefile, and `spec/`; RSpec, RuboCop with RSpec/Rake plugins, and Bundler gem tasks. Include `rubocop-prose`, `rubocop-md`, and `rubocop-spellcheck` in scaffold development dependencies and configure them for prose, Ruby code in Markdown, and spelling checks. Verify compatible latest stable releases and documented plugin loading so prose and embedded-Ruby checks coexist; include documentation in the lint command from the scaffold. Put runtime dependencies in the gemspec and development tooling in Gemfile; include source/issues/changelog metadata and RubyGems MFA metadata.
- JavaScript: npm, committed package-lock.json, `node --test`, ESLint, and ESM by default; use CommonJS when host compatibility requires it. Include ESLint with `@eslint/markdown` for source and embedded JavaScript code blocks, plus `markdownlint-cli2`, `markdownlint-rule-single-line-paragraphs`, and `markdownlint-rule-spellcheck` for Markdown prose and spelling in scaffold development dependencies. Use documented flat-config and Markdown processor integration, with code-block configuration matching actual examples; include both ESLint and markdownlint checks in `npm run lint`. Define exports, engines, and scripts; separate runtime, peer, and development dependencies.

## 3. Create the repository and scaffold PR

Validate scaffold setup, configured lint/test commands, and package construction; do not claim functionality is implemented. Commit the scaffold locally on the topic branch as one logical commit; include the Copilot co-author trailer. Unless the user limits the task to local work, use `gh` to create the GitHub repository, push the explicitly authorized README-only bootstrap base if needed, set `master` as the default branch, push the topic branch, and open the scaffold PR before implementing functionality. Beyond that authorized bootstrap, development changes go through PRs; direct pushes are reserved for explicitly authorized release automation.

Immediately after pushing the authorized bootstrap and setting the default branch, create an active branch ruleset using `gh api` before opening the scaffold PR, rather than a classic branch protection rule. Target `~DEFAULT_BRANCH`, with no bypass actors (including administrators), and block force pushes and branch deletion with `non_fast_forward` and `deletion` rules. Require pull requests using a `pull_request` rule unless an authorized release workflow needs direct pushes and no suitably scoped bypass is available; obtain authorization before removing that requirement and explain that all writers can then push directly. Do not require approving reviews unless requested. Keep authorized PR merges possible rather than restricting all branch updates. Read back the ruleset's enforcement, target conditions, bypass list, and rules to verify configuration; do not test by pushing to `master`. If the repository's plan or permissions prevent enforcement, report the limitation explicitly instead of claiming the ruleset is configured.

Configure repository merge options with `allow_squash_merge=true`, `allow_rebase_merge=true`, and `allow_merge_commit=false`, and enable automatic deletion of merged PR branches with `delete_branch_on_merge=true`; read them back to verify. Request a single coherent commit for most PRs, but allow multiple commits when they represent useful, independently reviewable changes.

Before every development push, including updates to an existing PR, run the project's local test and lint commands covering the pushed revision. Run final checks before committing and reuse their results for the push if the tested content and configuration have not changed; otherwise rerun affected checks. Fix failures before pushing, and report any check that cannot run rather than pushing unverified changes. The README-only bootstrap has no project checks yet; validate the scaffold before pushing its branch. Record these pre-push expectations in AGENTS and CONTRIBUTING.

For every PR, disclose AI authorship on behalf of `@dblock`, summarize scope and validation, and link related issues without closing them manually. Verify the remote branch, PR, and available CI results; report pending checks honestly.

Use a separate worktree and `<username>/<topic>` branch for each subsequent PR and prefer one logical commit unless multiple commits aid review. If its prerequisite PR is still unmerged, branch from that PR and target it with a stacked PR, stating the dependency; retarget to `master` after the base merges. Remove only worktrees you created when no longer needed and clean; never force removal of dirty worktrees. Do not merge, publish packages, create release tags/releases, or set registry credentials unless explicitly requested. Never overwrite existing repository work, published versions, or release tags.

## 4. Implement with tests

Write the agreed functionality, not just placeholders. Prefer the simplest design and existing public dependency APIs. Add focused behavior tests and real CLI/consumer integration tests where relevant; exercise public exports, configuration, errors, and meaningful edge cases. Example: [first implementation with explicit scope and real host integration](https://github.com/dblock/markdownlint-rule-spellcheck/pull/1).

## 5. Document

Keep README to bare-minimum installation and usage, status badges, and links to all project Markdown documents. Always include an explicit `## Usage` heading, separate from `## Installation`, with the smallest working example; in the scaffold, state clearly if usage is not implemented yet rather than inventing an example. As configurable features are added, put their options, defaults, and examples in a separate `## Configuration` section after Usage rather than expanding it. After Usage or Configuration, add `## Contributing` with links to CONTRIBUTING, DESIGN, CHANGELOG, RELEASING, and any other project documentation except the license, then `## License` with a link to the license file; do not replace these sections with a single “See ...” sentence. Add CHANGELOG, CONTRIBUTING, RELEASING, and DESIGN; document actual behavior and the agreed design. Keep Markdown paragraphs on one source line.

CONTRIBUTING starts with `# Contributing` and uses `## Setup and Validation` (requirements and actual install/test/lint/package/coverage commands), `## Tests` (test layout and real integration fixtures), and `## Pull Requests` (topic branches from `master`, request one coherent commit for most PRs, allow squash or rebase merges but not merge commits, affected documentation, changelog rules, and a RELEASING link). Include only applicable project specifics.

CHANGELOG starts with `# Changelog`, then `## <version> (Next)` and `- Your contribution here.` Within each version, list entries chronologically from oldest to newest; append new entries immediately above the placeholder, which stays last in the Next section. List release sections newest first with `## <version> (YYYY/MM/DD)`. Add entries for every feature, improvement, and fix, including meaningful tooling or documentation improvements; omit minor changes such as typos and the initial scaffold. Update an existing entry when appropriate rather than recording every unreleased implementation iteration. Use `- [#123](https://github.com/<owner>/<repo>/pull/123): Description - [@author](https://github.com/author).` with the contributor's actual attribution. Before opening a PR, query the latest repository issue or PR number, predict the next number, and use it in the entry so the first push has the intended format; issues and PRs share a sequence, and the prediction is not guaranteed. Immediately verify the assigned number after PR creation. If it differs, correct both label and URL, run applicable local checks, and update the PR branch; obtain authorization before amending an existing commit or force-pushing, and never force-push `master`. If the number cannot be reliably predicted, do not fabricate one: add its link after PR creation instead. Initial entries predating PRs go first in their version without PR or commit links.

RELEASING describes version synchronization, validation, authentication, exact-artifact publication, and registry/tag verification; it does not authorize publishing.

For Ruby projects, configure releases with [ruby-gem-release](https://github.com/dblock/ruby-gem-release): verify its current stable release and compatibility, add it as a development dependency, install its standard Rake tasks with the project's version and changelog formats, and add a manually dispatched `release.yml` calling its reusable workflow at the corresponding release tag. Follow its current sample and documentation for workflow inputs, permissions, and dry runs; document the `release` environment and RubyGems Trusted Publishing setup in RELEASING. Verify setup without publishing; do not create credentials, configure trusted publishers, alter protections, push release commits or tags, or dispatch a release without explicit authorization.

When the user authorizes a release workflow that prepares and pushes release metadata, atomically pushes the release commit and tag, and pushes the next development version, those automated updates do not require PRs. Document that exception in AGENTS, CONTRIBUTING, and RELEASING; keep ordinary development changes PR-based. Configure branch rules to permit the authorized workflow's fast-forward pushes without allowing force pushes or branch deletion. Prefer a dedicated release App bypass for only the PR requirement when supported; GitHub's built-in Actions integration may be rejected as a ruleset bypass actor in personal repositories. If so, obtain authorization before removing the ruleset's PR requirement, retain active `non_fast_forward` and `deletion` rules with no bypass actors, and explain that direct pushes are then permitted for all writers, not only the release workflow. Verify the effective rules through `gh api`, and do not create App credentials or publish without authorization.

## 6. Configure CI

Danger runs in PR context, not as a routine standalone local validation command; explain that distinction in CONTRIBUTING and AGENTS. Validate its actual PR CI result.

Use separate GitHub Actions workflow files: `test.yml` named `Test` for tests and coverage, `lint.yml` named `Lint` for code and documentation linting, and `package.yml` named `Package` for package validation. Do not combine tests and linting into a generic `ci.yml` or `CI` workflow. Use least-privilege permissions and dependency caching. Add runtime/host compatibility matrices and cross-platform checks when relevant. Add coverage with Coveralls. For Ruby projects, add Danger with `danger-pr-comment` and `danger-changelog` to development dependencies, configure a Dangerfile, and run Danger in PR CI with permissions needed for PR comments; verify each gem name resolves on RubyGems before installing. Keep changelog checks consistent with the project's exact changelog format: `danger-changelog`'s default Intridea placeholder is `* Your contribution here.`, and setting a dash placeholder may be normalized into an invalid `* - Your contribution here.` line. When the project requires a dash-style placeholder, do not call `changelog.check!` with that incompatible default parser; use a compatible changelog format or run only the update reminder, and state clearly which checks are enabled. Danger 9.6.1 fails to load with `git` 6.0.0 (`uninitialized constant Git::Base`); verify whether the upstream fix is available, and only while it is unresolved constrain `git` to `< 6`. For JavaScript projects, add Danger only when requested.

## 7. Validate and open the implementation PR

Once implementation is ready, run final tests, lint, and package validation before committing. Fix failures and rerun affected checks; avoid repeated intermediate full runs.

Build the gem with `bundle exec rake build` or create an npm tarball with `npm pack`. Inspect the archive's contents and install that actual artifact in an owned temporary consumer; verify public API/CLI behavior, not only source-tree tests. Validate workspace packages individually when applicable. Clean up only artifacts you created. Example: [exact-archive validation and release procedure](https://github.com/dblock/eslint-plugin-portable-paths/pull/9).

Commit the validated implementation and open its PR using the branch, attribution, and verification rules above.

## 8. Refine documentation linting

Documentation linting is configured in the scaffold for both ecosystems; refine it as implementation adds documentation, using a focused follow-up PR when needed. Enforce single-line prose paragraphs, add reviewed project vocabulary in `.spellcheck.txt`, exclude intentionally invalid fixtures and generated/vendor files, and fix typos rather than broadly suppressing checks. Check embedded Ruby with `rubocop-md` and embedded JavaScript with ESLint's Markdown processor. Include documentation checks in the normal lint command and `lint.yml` workflow. Example: [documentation spelling and single-line paragraph checks](https://github.com/dblock/markdownlint-rule-spellcheck/pull/6).

Validate affected checks before committing and opening the follow-up PR.

## 9. Create a logo in a follow-up PR

Agree on a logo concept reflecting the project's purpose before creating artwork. Save assets under `assets/` and retain editable sources when available. Put the logo first in README, followed by the project title, badges, and description, with blank lines between blocks; use an `<img>` with descriptive alt text and an explicit display width (160 pixels by default), as in [rubocop-prose's README](https://github.com/dblock/rubocop-prose/blob/main/README.md). Preserve upstream artwork and license notices when adapting existing assets; document provenance and regeneration instructions in DESIGN. Inspect both the full-size asset and README rendering for legibility and clipping. Examples: [RuboCop-inspired scroll](https://github.com/dblock/rubocop-prose/pull/60) and [portable-paths folder logo](https://github.com/dblock/eslint-plugin-portable-paths/pull/8).
