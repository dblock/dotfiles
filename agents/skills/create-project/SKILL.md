# Create Project

Create a small, working first version. Follow the workflow below; explicit user limits override its defaults.

Read the [shared development instructions](../../instructions.md) first. They define ongoing repository layout, Git and stacked-PR workflow, rebase merging, validation, dependency selection, documentation, changelogs/versioning, CI, and release safety. This skill adds project-creation steps and ecosystem-specific setup; do not duplicate or weaken the shared policy.

Prepare and validate the scaffold locally, then create the GitHub repository and open the scaffold as the first PR before implementing functionality. Include code and documentation linting in the scaffold; implementation and artwork follow in focused PRs.

Pause for user review and explicit approval after agreeing scope and design, after opening the scaffold PR, and after opening the implementation PR. Present the outcome and wait rather than automatically continuing. Incorporate requested adjustments into the current PR, validate, amend, and push without asking permission to update it; then wait for approval to proceed to the next phase. Resume from the current phase when the user says to continue. Also show logo concept previews and obtain approval of the selected preview before finalizing artwork. The benchmark, performance, CI-performance, and documentation-review steps below are focused follow-up PRs stacked in that order; pause after opening each. Local-only or other explicit user limits override these gates and PR steps.

## 1. Define and Agree

First ask for purpose, intended behavior, ecosystem, and project name, and explicitly agree with the user on the initial scope and non-goals before proceeding. Default GitHub owner to `dblock` and use the shared main-checkout and sibling-worktree layout.

Before creating a new project, search GitHub and the relevant package registry for very similar projects or libraries within the agreed scope. Compare the closest alternatives with links, covering overlapping functionality, meaningful differences or missing capabilities, maintenance, adoption, license, and runtime/host compatibility. Recommend whether to adopt or extend an existing project or create something new, with a concrete reason for any new project rather than assuming one is needed. Report search or access limitations instead of claiming no alternatives exist.

Present the comparison and recommendation, then obtain explicit agreement on whether to proceed with a new project and its final small first-version scope and non-goals. Agree on a brief design before scaffolding or implementing: public API/CLI, dependencies, host integration, and package/workspace layout.

Check repository and registry name availability early. Distinguish repository, registry package, scope, command, and plugin names; ask before changing the name or choosing a scope. An npm `E404` can indicate an unpublished name, but authentication/network errors cannot establish availability, and lookup cannot guarantee registry acceptance. Example: [scoped npm naming without changing the repository or command](https://github.com/dblock/oxlint-plugin-spellcheck/pull/15). A port may keep the original's crate, command, and formula names in a differently named repository, as [fue-rs](https://github.com/dblock/fue-rs) publishes the `fue` crate, binary, and Homebrew formula.

## 2. Scaffold

Create `~/source/<repo>/master` and initialize the repository there with `git init -b master`; `~/source/<repo>/` is the container for the main checkout and its sibling worktrees, not the Git repository itself. For a new repository without a base commit, ask for authorization to create and push a minimal README-only bootstrap commit on `master` so the scaffold PR has a base. This is the sole bootstrap exception to the PR-only rule; do not proceed without explicit authorization. If authorized, commit only a project title and brief description in README, including the Copilot co-author trailer, then switch to the scaffold topic branch before adding other files. Create the GitHub repository and push the bootstrap base only when the scaffold PR is ready. If authorization is declined, keep work local until the user provides a base. For an existing repository, inspect its status and worktrees without overwriting existing work; do not relocate an existing checkout without authorization. Subsequent development changes go through PRs; explicitly authorized release automation may push release and next-version commits directly as described below.

Use `<username>/scaffold`, `<username>/implementation`, and `<username>/logo` as topic-branch examples. Follow the shared branch, worktree, stacked-PR, commit, and cleanup policy throughout the creation workflow.

Use ecosystem tooling where useful, without overwriting existing work. Add package metadata, a version, public entry point, explicit packaged-file list, and MIT license. Choose supported runtimes from dependencies and host compatibility, not copied example versions.

Include the initial documentation and separate CI workflows described below in the scaffold PR; refine them after implementation. Keep release instructions explicitly provisional until release behavior exists. Add individual test, lint, and package badges to README. Avoid redundant Gemfile declarations for dependencies already provided by `gemspec`, and use narrowly scoped lint exceptions with concrete reasons rather than blanket cop disables. Latest scaffold example: [ruby-gem-release PR #1](https://github.com/dblock/ruby-gem-release/pull/1), covering package setup, AGENTS, contributor/design/release documents, documentation linting, and separate workflows. Use it as a reference, not a version-pinned template.

Configure scaffold linting to enforce title-case Markdown headings: for Ruby enable `Markdown/HeadingCapitalization` from `rubocop-prose` with `Style: title_case`; for JavaScript configure `eslint-plugin-markdown-preferences`'s `heading-casing` rule; for Rust enable rumdl's `MD063` with `style = "title_case"`, listing lowercase project names in `ignore-words`. Keep YAML workflow, job, and step display names in Title Case as a documented convention, preserving proper names, acronyms, identifiers, and expressions. No dedicated linting is needed for YAML display-name capitalization; do not add a custom checker solely for this convention. Include the conventions and actual lint commands in AGENTS and CONTRIBUTING.

Add `.gitignore` before installing dependencies or generating artifacts. For Ruby gems, ignore `.bundle/`, `Gemfile.lock`, `.rspec_status`, `coverage/`, `pkg/`, `vendor/`, and `.ruby-lsp/`; for JavaScript packages, ignore `node_modules/`, `coverage/`, and generated package tarballs, but commit `package-lock.json`; for Rust crates, ignore `target/` and coverage output such as `lcov.info`, but commit `Cargo.lock`. Ignore project-specific generated files and local secrets without hiding tracked sources, fixtures, or logo assets. Preserve existing ignore rules.

Add a root `AGENTS.md` with concise, actionable instructions for automated contributors; refine it after implementation. Start with `# Working on <project>` and a direction to read CONTRIBUTING and DESIGN. Cover the project's purpose and non-goals, implementation/test locations, supported runtimes and public dependency APIs, concrete invariants, prohibited shortcuts, and actual validation commands.

Carry the applicable shared maintenance policies into self-contained AGENTS and CONTRIBUTING guidance: repository layout and branch/worktree ownership, stacked PRs, coherent commits and rebase-only merging, guarded history updates, post-merge cleanup, tests/lint/package validation, dependency compatibility, documentation and artwork maintenance, changelogs/versioning, CI conventions, attribution, and release safety. Capture actual project commands and explicitly authorized release-automation exceptions, not this skill's one-time creation sequence. Contributors must not need access to personal Copilot instructions; link detailed project documents rather than repeating them throughout AGENTS.

Use concrete invariants, not generic advice: a spelling plugin might require offline dictionaries, original Unicode source offsets, and no global dependency mutation; a filesystem plugin might require read-only discovery, deterministic diagnostics, and real installed-CLI fixtures.

- Ruby: `lib/`, a version constant, gemspec, Gemfile, Rakefile, and `spec/`; RSpec, RuboCop with RSpec/Rake plugins, and Bundler gem tasks. Include `rubocop-prose`, `rubocop-md`, and `rubocop-spellcheck` in scaffold development dependencies and configure them for prose, Ruby code in Markdown, and spelling checks. Verify compatible latest stable releases and documented plugin loading so prose and embedded-Ruby checks coexist; include documentation in the lint command from the scaffold. Put runtime dependencies in the gemspec and development tooling in Gemfile; include source/issues/changelog metadata and RubyGems MFA metadata.
- JavaScript: npm, committed package-lock.json, `node --test`, ESLint, and ESM by default; use CommonJS when host compatibility requires it. Default to ESLint for source, embedded JavaScript, and Markdown: configure `@eslint/markdown`, `eslint-plugin-markdown-preferences` for Markdown style and title-case headings, `eslint-plugin-markdown-preferences-paragraph` with `width: "nowrap"` for single-line paragraphs, `eslint-plugin-prose-spellcheck` for prose spelling, `eslint-plugin-markdown-links` for missing local paths, and `eslint-plugin-markdown-links-unlinked` so every Markdown page is reachable from `README.md`, adding other entry points that readers or agents open directly as `roots`. Follow the [ESLint documentation linting example](https://github.com/dblock/eslint-plugin-markdown-preferences-paragraph/pull/4), using separate Markdown-source and code-block processor invocations when needed; include all checks in `npm run lint`. Verify current releases, compatibility, and documented configuration rather than inventing APIs. Configure `prose-spellcheck/spellcheck` with reviewed `.spellcheck.txt` vocabulary and retain `@cspell/dict-en_us` explicitly when supplying dictionaries. Define exports, engines, and scripts; separate runtime, peer, and development dependencies.
- Rust: Cargo with edition 2024, a library in `src/lib.rs` with a thin `src/main.rs` for binaries, unit tests beside the code, and CLI tests in `tests/`. Set `rust-version` to the oldest Rust that the runtime dependencies support and pin development to the current stable release in `rust-toolchain.toml` with the `clippy`, `rustfmt`, and `llvm-tools-preview` components; `llvm-tools-preview` lets `cargo llvm-cov` run without an interactive install prompt. Do not use language features newer than `rust-version` in `src`, such as let-chains before 1.88. Development dependencies may need newer Rust than the floor, so the floor CI job runs `cargo build --locked` and the current release runs `cargo test`. Use an explicit `include` list in Cargo.toml, and lint with `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, [rumdl](https://github.com/rvben/rumdl) for Markdown (title-case headings; disable `MD013` for single-line paragraphs), and [dylint-spellcheck](https://github.com/dblock/dylint-spellcheck) for spelling in code and Markdown with reviewed `.spellcheck.txt` vocabulary. With clap, pass `about` and `help` as explicit strings, including `#[value(help = "...")]` on value enums, because clap strips the trailing period from doc comments. For a command-line tool, add a release profile with `lto = true`, `codegen-units = 1`, and `strip = true`. Example: [fue-rs](https://github.com/dblock/fue-rs).

## 3. Create the Repository and Scaffold PR

Validate scaffold setup, configured lint/test commands, and package construction; do not claim functionality is implemented. Commit the scaffold locally on the topic branch as one logical commit; include your tool's AI co-author trailer. Unless the user limits the task to local work, use `gh` to create the GitHub repository, push the explicitly authorized README-only bootstrap base if needed, set `master` as the default branch, push the topic branch, and open the scaffold PR before implementing functionality. Beyond that authorized bootstrap, development changes go through PRs; direct pushes are reserved for explicitly authorized release automation.

Immediately after pushing the authorized bootstrap and setting the default branch, create an active branch ruleset using `gh api` before opening the scaffold PR, rather than a classic branch protection rule. Target `~DEFAULT_BRANCH`, with no bypass actors (including administrators), and block force pushes and branch deletion with `non_fast_forward` and `deletion` rules. Require pull requests using a `pull_request` rule except when setting up an authorized trusted-release flow, which requires direct pushes as described below. Do not require approving reviews unless requested. Keep authorized PR merges possible rather than restricting all branch updates. Read back the ruleset's enforcement, target conditions, bypass list, and rules to verify configuration; do not test by pushing to `master`. If the repository's plan or permissions prevent enforcement, report the limitation explicitly instead of claiming the ruleset is configured.

Configure repository merge options with `allow_squash_merge=false`, `allow_rebase_merge=true`, and `allow_merge_commit=false`, and enable automatic deletion of merged PR branches with `delete_branch_on_merge=true`; read them back to verify. This implements the shared unconditional rebase-merge preference.

Apply the shared validation, attribution, and PR-verification rules to every push and PR. The README-only bootstrap has no project checks yet; validate the scaffold before pushing its branch. Use the shared stacked-PR workflow for subsequent changes while preserving this skill's review gates.

## 4. Implement With Tests

Write the agreed functionality, not just placeholders, using the shared implementation and behavioral-testing policy. For host plugins, establish the real AST, source coordinates, and callback lifecycle before designing configuration. Before writing generic or repeated functionality such as test sharding, parsing, retries, or file matching, search for an existing library and prefer it when it is actively maintained (recent releases, responsive issues), widely used, compatibly licensed, and supports the project's runtimes; keep custom code only for project-specific behavior or when no suitable library exists, and note the choice in DESIGN. For example, [posebook replaced a custom RSpec shard script with `parallel_tests`](https://github.com/dblock/posebook/pull/181). Native ESLint Markdown uses mdast and source positions, not ESTree `Program`/`range`; explicitly reconcile synchronous rule creation with dictionary preparation.

For Rust HTTP clients, use reqwest without default features, enabling only what is needed (such as `rustls` and `json`), with tokio. For GraphQL APIs, use graphql_client typed queries against a vendored schema whose source commit and license are recorded beside it. graphql_client ignores `@include` and `@skip`, so split conditional selections into separate queries, and guard new non-null fields that older recorded responses lack. Test HTTP behavior with wiremock, the CLI with assert_cmd subprocess tests, and use `example.com` addresses rather than real people's in fixtures. Measure coverage with `cargo llvm-cov` (run it with `< /dev/null` in non-interactive shells). When performance matters, add criterion benchmarks against realistic mocked latency and run them once in CI with `cargo bench --locked --benches -- --test`; report measured before-and-after numbers in the PR.

When implementing release tooling, follow the shared isolated-testing policy and cover hook ordering, failed remote pushes, delayed registry visibility and timeout, and verification after the manifest advances. Test actual npm pack/view JSON shapes across supported tooling versions. With `npx -c` tooling wrappers, inherited `npm_config_call` and `npm_config_package` can break nested npm exec; prefer a clean runtime PATH or remove only those wrapper variables, not change project code to accommodate the wrapper.

During the initial implementation, aim for coverage close to 100% of project-owned runtime code. Inspect line and branch coverage where supported, and add meaningful behavior tests for uncovered paths, especially errors and edge cases; include CLI subprocess coverage where applicable. Do not inflate coverage with trivial assertions or exclude real implementation code to improve the percentage. Report remaining gaps and their reasons rather than imposing a blanket 100% threshold. Include this testing expectation and the coverage command in AGENTS and CONTRIBUTING.

## 5. Document

Create README, CHANGELOG, CONTRIBUTING, RELEASING, and DESIGN using the shared documentation and changelog conventions. README must have explicit `## Installation`, `## Usage`, `## Contributing`, and `## License` sections, plus `## Configuration` after Usage when needed. In the scaffold, state clearly if usage is not implemented yet rather than inventing an example.

CONTRIBUTING starts with `# Contributing` and uses `## Setup and Validation` (requirements and actual install/test/lint/package/coverage commands), `## Tests` (test layout and real integration fixtures), and `## Pull Requests` (the applicable shared branch, stacked-PR, commit, and rebase-only merge policy, affected documentation, changelog rules, and a RELEASING link). Include only applicable project specifics.

For CLIs, include a tiny representative output example and define ordering, deduplication, location units, output channels, and incompatible flags in the appropriate command guide. Keep machine-consumable vocabulary separate from human review reports; exercise source and installed executables with shared fixtures. Example: [reviewed CLI context output](https://github.com/dblock/eslint-plugin-prose-spellcheck/pull/10).

RELEASING describes version synchronization, validation, authentication, exact-artifact publication, and registry/tag verification; it does not authorize publishing.

For JavaScript packages, configure releases with [npm-package-release](https://github.com/dblock/npm-package-release); do not publish any version manually. Verify its current stable release and follow its README and detailed usage guide rather than remembered steps. Keep the checked-in version at an unpublished `0.1.0`: the release workflow publishes the first real version through npm Trusted Publishing, after a deprecated `0.0.0` placeholder reserves the name, because npm configures a trusted publisher only for an existing package. Document this flow in RELEASING and AGENTS. Publication, placeholder reservation, tags/releases, authentication, and trusted-publisher setup each require explicit user authorization; writing these instructions does not perform or authorize a release.

Set up release automation in a focused PR once the implementation is ready. Install `npm-package-release` as an exact development dependency, add `npr.config.js` exporting a `createReleaseWorkflow(services)` builder with the changelog class matching the project's format (`IntrideaChangelog` for `## 0.1.0 (Next)`), a validator that runs the packed-consumer check against the exact archive (`PACKAGE_ARCHIVE`), and `releaseReferences` for files that pin the released version, such as README install snippets or workflow and action version pins that callers reference by tag. Add a manually dispatched `release.yml` calling `dblock/npm-package-release/.github/workflows/release.yml` at the tag matching the dependency, with `contents: write` and `id-token: write`, and upgrade the dependency and pin together; do not add a `release` npm script that could publish by accident. Add a release test that runs the real workflow builder with npm-package-release's testing services, simulated publication and hosting, and a local Git remote, checking the dated changelog, tag, next development commit, version pins, and byte-identical archives. The release workflow uses its own npm version, so packed-consumer tests must accept every supported `npm pack --json` shape (npm 11 prints an array, npm 12 an object keyed by package name), and Package CI must include an entry on the npm version `release.yml` passes. npm-package-release already orders validation, publication, atomic pushes, GitHub Release creation, next-development preparation, bounded registry visibility checks, recovery artifacts, and verification; do not reimplement them. Before the first real release, dry-run with `npr reserve --dry-run`, `npr trust --dry-run`, and `npr prepare` in an isolated clone with a local bare remote.

After a dispatch, verify the run, the explicit version on npm with provenance, matching SHA-1 and SHA-512 checksums for the registry tarball, GitHub Release asset, and retained artifacts, the tag on the release commit, the GitHub Release, and the next development commit. A dispatch is not confirmation of publication; a failed validation publishes nothing, so fix it in a PR and dispatch again, and inspect recovery artifacts before retrying an ambiguous run. Example: [release automation](https://github.com/dblock/eslint-plugin-markdown-links-unlinked/pull/11) and [npm 12 pack output](https://github.com/dblock/eslint-plugin-markdown-links-unlinked/pull/12).

For both JavaScript and Ruby trusted-publishing flows, configure the `release` environment for the default branch without required reviewers or deployment approval gates unless the user explicitly requests them. Release workflows must push release metadata and the next development version directly to `master`, not open PRs for those updates. When authorized to set up either flow, remove any ruleset or classic protection requirement for PRs that blocks it, retaining active force-push and branch-deletion protections with no bypass actors. Verify effective rules and document in AGENTS, CONTRIBUTING, and RELEASING that removing the PR requirement permits direct pushes by all writers, not only the workflow; ordinary development still follows the project's PR convention. Release setup authorization covers these necessary protection changes, not release dispatch, publication, or tags.

With authorization, reserve and trust a new package by having the user run `npm exec --offline -- npr bootstrap` from the package checkout in their own terminal, after `npm login` (preview first with `--dry-run`). npm requires browser 2FA for publish, deprecate, and trust, which a non-interactive agent shell cannot complete; never request codes or tokens in chat. For a package that already exists on npm, use `npr trust` instead. Check that `npm trust list` shows the actual owner/repository, `release.yml`, environment `release`, and direct publication rather than stage-only; configuration alone does not prove OIDC publication, and a new publisher must publish successfully within two days or expire, so dispatch the first release promptly. npm may still be processing the new placeholder when `npr bootstrap` deprecates it, leaving it without a deprecation notice; deprecate `0.0.0` after the first release instead, which is optional and does not affect publication. Apply the authorized release-setup protection policy above; never reuse another repository's authorization or weaken force-push/deletion protections. Run tests/lint before pushing, add a concise changelog entry, and pause after opening the PR; do not merge, dispatch, publish, or tag without authorization.

For Ruby projects, configure releases with [ruby-gem-release](https://github.com/dblock/ruby-gem-release): verify its current stable release and compatibility, add it as a development dependency, install its standard Rake tasks with the project's version and changelog formats, and add a manually dispatched `release.yml` calling its reusable workflow at the corresponding release tag. Its clean-checkout check rejects untracked files, so make sure `.gitignore` covers `vendor/bundle` (where Bundler installs gems in CI), `.bundle/`, and `Gemfile.lock` or a committed lockfile, including when adding release automation to an existing gem; otherwise the dry run fails before any other check. Follow its current sample and documentation for workflow inputs, permissions, and dry runs; document the `release` environment and RubyGems Trusted Publishing setup in RELEASING. Apply the shared authorized release-setup protection policy above. Verify setup without publishing; credentials, trusted-publisher setup, release commits/tags, and release dispatch still require explicit authorization. [scripts/publisher.rb](scripts/publisher.rb) is the script used to configure strava-ruby-client's RubyGems trusted publisher with `create` and list it with `list`, each taking the current MFA code.

For Rust projects, configure releases with [rust-crate-release](https://github.com/dblock/rust-crate-release): verify its current stable release, and add a manually dispatched `release.yml` on the default branch calling its reusable workflow with the matching `tool-ref`. crates.io Trusted Publishing works only for a crate that already exists, so plan a manual first `cargo publish` of `0.1.0` by the user, then configure the trusted publisher with `crates-trusted-publisher` (see the shared instructions) and release `0.1.1` and later through the workflow. rust-crate-release rejects release notes that contain only the changelog placeholder, so the `0.1.1` section needs a real entry, such as the prebuilt binaries it is the first to ship. Apply the shared authorized release-setup protection policy above.

For command-line crates, ship prebuilt binaries. Add a reusable `binaries.yml` that Package calls on every PR and push without uploading, and that Release calls with the new tag to upload. Build each target natively on its own GitHub-hosted runner, such as `aarch64-apple-darwin` on `macos-15`, `x86_64-apple-darwin` on `macos-15-intel`, `aarch64-unknown-linux-musl` on `ubuntu-24.04-arm`, `x86_64-unknown-linux-musl` on `ubuntu-24.04`, and `x86_64-pc-windows-msvc` on `windows-2025`; verify current runner labels. Check that each binary's `--version` matches the crate version and that musl binaries are statically linked (`file` reports either `statically linked` or `static-pie linked`), and publish `<name>-<version>-<target>.tar.gz` (`.zip` on Windows) with README, CHANGELOG, and LICENSE, plus a `.sha256` file for each archive.

Publish a formula to the shared [dblock/homebrew-tap](https://github.com/dblock/homebrew-tap), generated from the release's `.sha256` files by its updater and scheduled update workflow, so users run `brew install dblock/tap/<name>`. `brew tap` clones a local tap directory, so the update workflow commits generated formulae before auditing, installing, and testing them, and pushes only after those pass. Document Homebrew, the release downloads, and `cargo install <crate>` in README's Installation.

## 6. Configure CI

Create the shared separate Test, Lint, and Package workflows with explicit `matrix.entry` combinations, least-privilege permissions, caching, and relevant compatibility coverage. Give each workflow a `concurrency` group keyed by workflow and ref (`group: ${{ github.workflow }}-${{ github.ref }}`) that cancels superseded pull request runs without canceling default-branch runs (`cancel-in-progress: ${{ github.event_name == 'pull_request' }}`); it saves runner time when a stack is rebased or amended, not job time. Add coverage with Coveralls. Record the CI conventions and the distinction between local validation and PR-only Danger checks in AGENTS and CONTRIBUTING.

For Ruby projects, add Danger with `danger-pr-comment` and `danger-changelog` to development dependencies, configure a Dangerfile, and run Danger in PR CI with permissions needed for PR comments; set `comment-empty: false` on the `danger-pr-comment` comment workflow so pull requests without findings get no comment (an existing comment is still updated when its findings clear); verify each gem name resolves on RubyGems before installing. Keep changelog checks consistent with the project's exact changelog format: `danger-changelog`'s default Intridea placeholder is `* Your contribution here.`, and setting a dash placeholder may be normalized into an invalid `* - Your contribution here.` line. When the project requires a dash-style placeholder, do not call `changelog.check!` with that incompatible default parser; use a compatible changelog format or run only the update reminder, and state clearly which checks are enabled. Danger 9.6.1 fails to load with `git` 6.0.0 (`uninitialized constant Git::Base`); verify whether the upstream fix is available, and only while it is unresolved constrain `git` to `< 6`. For JavaScript and Rust projects, add Danger only when requested.

For Rust projects, cache with `Swatinem/rust-cache`, use one Test job whose `matrix.entry` combines `rust` and `command` (the `rust-version` floor with `build` on Linux; the current release with `test` on Linux, macOS, and Windows), and add Coverage (`cargo llvm-cov --lcov` to Coveralls) and, when benchmarks exist, Benchmarks jobs. Lint runs Rust (fmt and clippy), Markdown (`rvben/rumdl` action), and Spelling (Dylint) jobs, and Package runs `cargo package --locked` and a clean `cargo install` of the packaged crate.

## 7. Validate and Open the Implementation PR

Once implementation is ready, apply the shared final-validation policy before committing and opening its PR.

Build the gem with `bundle exec rake build`, create an npm tarball with `npm pack`, or package the crate with `cargo package --locked` and install it with `cargo install --path` from the unpacked `target/package` directory into a temporary root, then perform the shared real-artifact consumer validation. Examples: [exact-archive validation and release procedure](https://github.com/dblock/eslint-plugin-portable-paths/pull/9) and [empty-archive override regression and recovery](https://github.com/dblock/eslint-plugin-markdown-preferences-paragraph/pull/18).

Commit the validated implementation and open its PR using the shared branch, attribution, and verification rules; pause for the required review.

## 8. Refine Documentation Linting

Documentation linting is configured in the scaffold for both ecosystems; refine it as implementation adds documentation, using a focused follow-up PR when needed. Apply the shared documentation-linting policy. Check embedded Ruby with `rubocop-md` and embedded JavaScript with ESLint's Markdown processor. Use ESLint for all JavaScript project documentation checks, and rumdl and dylint-spellcheck for Rust projects.

Validate affected checks before committing and opening the follow-up PR.

## 9. Create a Logo in a Follow-up PR

Propose 3–5 distinct, creative logo concepts reflecting the project's purpose and show quick, clearly labeled visual previews before asking the user to choose one. Prefer a comparison sheet with consistent scale and presentation; do not require a choice based on text descriptions alone. Obtain any required image-generation authorization before rendering. Keep draft previews in session artifacts rather than committing unselected concepts.

Iterate on previews with the user before committing to a direction. When refining a chosen preview, use it as the reference and preserve its composition except for the requested changes. Obtain explicit approval of the selected preview before finalizing artwork or opening the logo PR.

Save approved assets under `assets/` and retain editable sources when available. When the logo is generated or rendered by code, write that script in the project's own language (Ruby for gems, JavaScript for packages, Rust for crates) and run it with the project's tooling, so contributors can regenerate artwork without other runtimes. For a crate, generate it from `examples/logo.rs` with `cargo run --example logo`, mark that example `test = true` with a test that compares its output with the committed asset, and add `<asset> text eol=lf` to `.gitattributes` so the comparison passes on Windows. Put the logo first in README, followed by the project title, badges, and description, with blank lines between blocks; use an `<img>` with descriptive alt text and an explicit display width (160 pixels by default), as in [rubocop-prose's README](https://github.com/dblock/rubocop-prose/blob/main/README.md). Preserve upstream artwork and license notices when adapting existing assets; document provenance and regeneration instructions in DESIGN. Inspect both the full-size asset and README rendering for legibility and clipping. Examples: [RuboCop-inspired scroll](https://github.com/dblock/rubocop-prose/pull/60) and [portable-paths folder logo](https://github.com/dblock/eslint-plugin-portable-paths/pull/8).

## 10. Add Benchmarks in a Follow-up PR

Add benchmarks once the implementation exists, so later performance work has a baseline. Use a maintained benchmark library rather than hand-rolled timers: [criterion](https://github.com/bheisler/criterion.rs) for Rust as described above, [`tinybench`](https://github.com/tinylibs/tinybench) or a verified current alternative for JavaScript, and [`benchmark-ips`](https://github.com/evanphx/benchmark-ips) or a verified current alternative for Ruby; record the choice in DESIGN. Generate realistic, deterministic inputs with a seeded generator at several sizes and shapes (for example 100, 1,000, and 5,000 items) in owned temporary directories instead of committing large fixtures, and before timing, check that each run still produces the expected results so a benchmark cannot measure broken behavior. Measure each expensive phase separately and the end-to-end path through the public entry point or host (for example a full ESLint run with and without the rule, reporting the plugin's overhead).

Provide a full command (`npm run bench`, `rake bench`, or `cargo bench`) and a quick profile, and run the quick profile once in CI as a Benchmarks job that posts its table to the job summary. Report timings without asserting thresholds, because runners vary. Document how to run and compare benchmarks in CONTRIBUTING, and in AGENTS require keeping them working and reporting measured before-and-after numbers for performance changes. Include a baseline results table, with the runtime version and CPU, in the PR.

## 11. Improve Performance in a Follow-up PR

Stack performance work on the benchmark PR. Profile before changing code (for example `node --cpu-prof`, `cargo flamegraph`, or `stackprof`) at realistic sizes, and optimize only measured hot spots, keeping behavior identical: existing tests pass unchanged, new code paths get tests, and coverage stays where it was. Prefer simple changes such as avoiding repeated work, caching with explicit invalidation, and better data structures. Reject shortcuts that are not equivalent; when a faster parser or algorithm is tempting, test parity against the full implementation across fixtures and generated inputs, and record rejected options and why in DESIGN. Compare the same command on the base and the change on the same idle machine over several alternating runs, report medians and each optimization's individual impact in the PR, and keep DESIGN to the resulting design and its rationale rather than a profiling diary.

## 12. Review CI Performance in a Follow-up PR

Analyze CI timing directly with `gh run list` and `gh api repos/<owner>/<repo>/actions/runs/<id>/jobs`, comparing per-job and per-step durations across several recent runs, rather than guessing. Look for easy wins: missing dependency caching, redundant installs or matrix entries, slow steps that repeat work, and a missing `concurrency` group (see Configure CI), which is kept for the runner time it saves even though it does not shorten jobs. Do not weaken coverage of supported runtimes, operating systems, or real-artifact validation to save time. Measure each change on the PR's own runs against its base, report before-and-after job times, and drop changes that show no measurable improvement instead of keeping them as noise; single runs vary by several seconds, so compare steps, not only totals. Document retained CI conventions in AGENTS and CONTRIBUTING.

## 13. Review Documentation for End Users in a Follow-up PR

Review all Markdown once the project's behavior has settled, reading README as someone installing the package for the first time. Lead with what the project does and a tiny example of its output, keep Installation and Usage minimal and ready to copy and paste, explain only the behavior users need to predict results, and show configuration examples as the smallest addition to the Usage setup rather than repeating it. Clarify options users are likely to confuse with a one-line distinction and an example each, state requirements as exact version ranges, and move caveats into a short Limitations list. Verify every documented behavior, default, and message against the code. Write the user-facing documentation as if the first release (`0.1.0`) were already published, so it is ready on release day without another pass: drop "not published yet" and "once released" caveats, use the real registry install command, and describe the package as available, while keeping the version itself, CHANGELOG `(Next)` heading, and RELEASING unchanged until the release actually happens.

Simplify contributor documents without losing invariants: DESIGN links to README for user-facing options and limitations instead of repeating them and keeps current design and rationale only; long paragraphs that enumerate files, invariants, or steps become lists in CONTRIBUTING and AGENTS; remove duplicated or superseded text. Run the documentation lint, including any link and spelling checks, and add a changelog entry for meaningful documentation improvements.
