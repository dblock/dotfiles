# Create project

Create a small, working first version. Follow the workflow below; explicit user limits override its defaults.

Read the [shared development instructions](../../instructions.md) first. They define ongoing repository layout, Git and stacked-PR workflow, rebase merging, validation, dependency selection, documentation, changelogs/versioning, CI, and release safety. This skill adds project-creation steps and ecosystem-specific setup; do not duplicate or weaken the shared policy.

Prepare and validate the scaffold locally, then create the GitHub repository and open the scaffold as the first PR before implementing functionality. Include code and documentation linting in the scaffold; implementation and artwork follow in focused PRs.

Pause for user review and explicit approval after agreeing scope and design, after opening the scaffold PR, and after opening the implementation PR. Present the outcome and wait rather than automatically continuing. Incorporate requested adjustments into the current PR, validate, amend, and push without asking permission to update it; then wait for approval to proceed to the next phase. Resume from the current phase when the user says to continue. Also show logo concept previews and obtain approval of the selected preview before finalizing artwork. Local-only or other explicit user limits override these gates and PR steps.

## 1. Define and Agree

First ask for purpose, intended behavior, ecosystem, and project name, and explicitly agree with the user on the initial scope and non-goals before proceeding. Default GitHub owner to `dblock` and use the shared main-checkout and sibling-worktree layout.

Before creating a new project, search GitHub and the relevant package registry for very similar projects or libraries within the agreed scope. Compare the closest alternatives with links, covering overlapping functionality, meaningful differences or missing capabilities, maintenance, adoption, license, and runtime/host compatibility. Recommend whether to adopt or extend an existing project or create something new, with a concrete reason for any new project rather than assuming one is needed. Report search or access limitations instead of claiming no alternatives exist.

Present the comparison and recommendation, then obtain explicit agreement on whether to proceed with a new project and its final small first-version scope and non-goals. Agree on a brief design before scaffolding or implementing: public API/CLI, dependencies, host integration, and package/workspace layout.

Check repository and registry name availability early. Distinguish repository, registry package, scope, command, and plugin names; ask before changing the name or choosing a scope. An npm `E404` can indicate an unpublished name, but authentication/network errors cannot establish availability, and lookup cannot guarantee registry acceptance. Example: [scoped npm naming without changing the repository or command](https://github.com/dblock/oxlint-plugin-spellcheck/pull/15).

## 2. Scaffold

Create `~/source/<repo>/master` and initialize the repository there with `git init -b master`; `~/source/<repo>/` is the container for the main checkout and its sibling worktrees, not the Git repository itself. For a new repository without a base commit, ask for authorization to create and push a minimal README-only bootstrap commit on `master` so the scaffold PR has a base. This is the sole bootstrap exception to the PR-only rule; do not proceed without explicit authorization. If authorized, commit only a project title and brief description in README, including the Copilot co-author trailer, then switch to the scaffold topic branch before adding other files. Create the GitHub repository and push the bootstrap base only when the scaffold PR is ready. If authorization is declined, keep work local until the user provides a base. For an existing repository, inspect its status and worktrees without overwriting existing work; do not relocate an existing checkout without authorization. Subsequent development changes go through PRs; explicitly authorized release automation may push release and next-version commits directly as described below.

Use `<username>/scaffold`, `<username>/implementation`, and `<username>/logo` as topic-branch examples. Follow the shared branch, worktree, stacked-PR, commit, and cleanup policy throughout the creation workflow.

Use ecosystem tooling where useful, without overwriting existing work. Add package metadata, a version, public entry point, explicit packaged-file list, and MIT license. Choose supported runtimes from dependencies and host compatibility, not copied example versions.

Include the initial documentation and separate CI workflows described below in the scaffold PR; refine them after implementation. Keep release instructions explicitly provisional until release behavior exists. Add individual test, lint, and package badges to README. Avoid redundant Gemfile declarations for dependencies already provided by `gemspec`, and use narrowly scoped lint exceptions with concrete reasons rather than blanket cop disables. Latest scaffold example: [ruby-gem-release PR #1](https://github.com/dblock/ruby-gem-release/pull/1), covering package setup, AGENTS, contributor/design/release documents, documentation linting, and separate workflows. Use it as a reference, not a version-pinned template.

Configure scaffold linting to enforce title-case Markdown headings: for Ruby enable `Markdown/HeadingCapitalization` from `rubocop-prose` with `Style: title_case`; for JavaScript configure `eslint-plugin-markdown-preferences`'s `heading-casing` rule. Keep YAML workflow, job, and step display names in Title Case as a documented convention, preserving proper names, acronyms, identifiers, and expressions. No dedicated linting is needed for YAML display-name capitalization; do not add a custom checker solely for this convention. Include the conventions and actual lint commands in AGENTS and CONTRIBUTING.

Add `.gitignore` before installing dependencies or generating artifacts. For Ruby gems, ignore `.bundle/`, `Gemfile.lock`, `.rspec_status`, `coverage/`, `pkg/`, `vendor/`, and `.ruby-lsp/`; for JavaScript packages, ignore `node_modules/`, `coverage/`, and generated package tarballs, but commit `package-lock.json`. Ignore project-specific generated files and local secrets without hiding tracked sources, fixtures, or logo assets. Preserve existing ignore rules.

Add a root `AGENTS.md` with concise, actionable instructions for automated contributors; refine it after implementation. Start with `# Working on <project>` and a direction to read CONTRIBUTING and DESIGN. Cover the project's purpose and non-goals, implementation/test locations, supported runtimes and public dependency APIs, concrete invariants, prohibited shortcuts, and actual validation commands.

Carry the applicable shared maintenance policies into self-contained AGENTS and CONTRIBUTING guidance: repository layout and branch/worktree ownership, stacked PRs, coherent commits and rebase-only merging, guarded history updates, post-merge cleanup, tests/lint/package validation, dependency compatibility, documentation and artwork maintenance, changelogs/versioning, CI conventions, attribution, and release safety. Capture actual project commands and explicitly authorized release-automation exceptions, not this skill's one-time creation sequence. Contributors must not need access to personal Copilot instructions; link detailed project documents rather than repeating them throughout AGENTS.

Use concrete invariants, not generic advice: a spelling plugin might require offline dictionaries, original Unicode source offsets, and no global dependency mutation; a filesystem plugin might require read-only discovery, deterministic diagnostics, and real installed-CLI fixtures.

- Ruby: `lib/`, a version constant, gemspec, Gemfile, Rakefile, and `spec/`; RSpec, RuboCop with RSpec/Rake plugins, and Bundler gem tasks. Include `rubocop-prose`, `rubocop-md`, and `rubocop-spellcheck` in scaffold development dependencies and configure them for prose, Ruby code in Markdown, and spelling checks. Verify compatible latest stable releases and documented plugin loading so prose and embedded-Ruby checks coexist; include documentation in the lint command from the scaffold. Put runtime dependencies in the gemspec and development tooling in Gemfile; include source/issues/changelog metadata and RubyGems MFA metadata.
- JavaScript: npm, committed package-lock.json, `node --test`, ESLint, and ESM by default; use CommonJS when host compatibility requires it. Default to ESLint for source, embedded JavaScript, and Markdown: configure `@eslint/markdown`, `eslint-plugin-markdown-preferences` for Markdown style and title-case headings, `eslint-plugin-markdown-preferences-paragraph` with `width: "nowrap"` for single-line paragraphs, and `eslint-plugin-prose-spellcheck` for prose spelling. Follow the [ESLint documentation linting example](https://github.com/dblock/eslint-plugin-markdown-preferences-paragraph/pull/4), using separate Markdown-source and code-block processor invocations when needed; include all checks in `npm run lint`. Verify current releases, compatibility, and documented configuration rather than inventing APIs. Configure `prose-spellcheck/spellcheck` with reviewed `.spellcheck.txt` vocabulary and retain `@cspell/dict-en_us` explicitly when supplying dictionaries. Define exports, engines, and scripts; separate runtime, peer, and development dependencies.

## 3. Create the repository and scaffold PR

Validate scaffold setup, configured lint/test commands, and package construction; do not claim functionality is implemented. Commit the scaffold locally on the topic branch as one logical commit; include your tool's AI co-author trailer. Unless the user limits the task to local work, use `gh` to create the GitHub repository, push the explicitly authorized README-only bootstrap base if needed, set `master` as the default branch, push the topic branch, and open the scaffold PR before implementing functionality. Beyond that authorized bootstrap, development changes go through PRs; direct pushes are reserved for explicitly authorized release automation.

Immediately after pushing the authorized bootstrap and setting the default branch, create an active branch ruleset using `gh api` before opening the scaffold PR, rather than a classic branch protection rule. Target `~DEFAULT_BRANCH`, with no bypass actors (including administrators), and block force pushes and branch deletion with `non_fast_forward` and `deletion` rules. Require pull requests using a `pull_request` rule except when setting up an authorized trusted-release flow, which requires direct pushes as described below. Do not require approving reviews unless requested. Keep authorized PR merges possible rather than restricting all branch updates. Read back the ruleset's enforcement, target conditions, bypass list, and rules to verify configuration; do not test by pushing to `master`. If the repository's plan or permissions prevent enforcement, report the limitation explicitly instead of claiming the ruleset is configured.

Configure repository merge options with `allow_squash_merge=false`, `allow_rebase_merge=true`, and `allow_merge_commit=false`, and enable automatic deletion of merged PR branches with `delete_branch_on_merge=true`; read them back to verify. This implements the shared unconditional rebase-merge preference.

Apply the shared validation, attribution, and PR-verification rules to every push and PR. The README-only bootstrap has no project checks yet; validate the scaffold before pushing its branch. Use the shared stacked-PR workflow for subsequent changes while preserving this skill's review gates.

## 4. Implement with tests

Write the agreed functionality, not just placeholders, using the shared implementation and behavioral-testing policy. For host plugins, establish the real AST, source coordinates, and callback lifecycle before designing configuration. Before writing generic or repeated functionality such as test sharding, parsing, retries, or file matching, search for an existing library and prefer it when it is actively maintained (recent releases, responsive issues), widely used, compatibly licensed, and supports the project's runtimes; keep custom code only for project-specific behavior or when no suitable library exists, and note the choice in DESIGN. For example, [posebook replaced a custom RSpec shard script with `parallel_tests`](https://github.com/dblock/posebook/pull/181). Native ESLint Markdown uses mdast and source positions, not ESTree `Program`/`range`; explicitly reconcile synchronous rule creation with dictionary preparation.

When implementing release tooling, follow the shared isolated-testing policy and cover hook ordering, failed remote pushes, delayed registry visibility and timeout, and verification after the manifest advances. Test actual npm pack/view JSON shapes across supported tooling versions. With `npx -c` tooling wrappers, inherited `npm_config_call` and `npm_config_package` can break nested npm exec; prefer a clean runtime PATH or remove only those wrapper variables, not change project code to accommodate the wrapper.

During the initial implementation, aim for coverage close to 100% of project-owned runtime code. Inspect line and branch coverage where supported, and add meaningful behavior tests for uncovered paths, especially errors and edge cases; include CLI subprocess coverage where applicable. Do not inflate coverage with trivial assertions or exclude real implementation code to improve the percentage. Report remaining gaps and their reasons rather than imposing a blanket 100% threshold. Include this testing expectation and the coverage command in AGENTS and CONTRIBUTING.

## 5. Document

Create README, CHANGELOG, CONTRIBUTING, RELEASING, and DESIGN using the shared documentation and changelog conventions. README must have explicit `## Installation`, `## Usage`, `## Contributing`, and `## License` sections, plus `## Configuration` after Usage when needed. In the scaffold, state clearly if usage is not implemented yet rather than inventing an example.

CONTRIBUTING starts with `# Contributing` and uses `## Setup and Validation` (requirements and actual install/test/lint/package/coverage commands), `## Tests` (test layout and real integration fixtures), and `## Pull Requests` (the applicable shared branch, stacked-PR, commit, and rebase-only merge policy, affected documentation, changelog rules, and a RELEASING link). Include only applicable project specifics.

For CLIs, include a tiny representative output example and define ordering, deduplication, location units, output channels, and incompatible flags in the appropriate command guide. Keep machine-consumable vocabulary separate from human review reports; exercise source and installed executables with shared fixtures. Example: [reviewed CLI context output](https://github.com/dblock/eslint-plugin-prose-spellcheck/pull/10).

RELEASING describes version synchronization, validation, authentication, exact-artifact publication, and registry/tag verification; it does not authorize publishing.

For JavaScript packages, plan a manual first npm release at `0.1.0`, then configure npm Trusted Publishing for subsequent releases after the package exists. Document this sequence in RELEASING and AGENTS: validate and inspect the actual npm tarball, publish that artifact manually with explicitly authorized interactive authentication, and verify the registry version and matching release tag. Only afterward configure the package's trusted publisher and a GitHub Actions release workflow using OIDC, following current npm requirements; do not store long-lived npm tokens in repository secrets. Publication, tags/releases, authentication, and trusted-publisher setup each require explicit user authorization; writing these instructions does not perform or authorize a release.

Set up JavaScript trusted publishing in a focused PR after verifying the initial registry release, existing tooling, repository instructions, default branch, and protections; do not perform another bootstrap publication. Read the reference repository's current `release.yml`, `.release-it.json`, `scripts/release.js`, `test/release.test.js`, and RELEASING rather than copying obsolete historical names. Reuse tooling and adapt hooks in this order: validate the exact archive, publish it, atomically push the matching release commit/tag, verify remote release refs, create the GitHub Release, validate and push the next development version, then confirm the published version and retained archive integrity. Final verification uses the explicit released version and retained archive, never the now-advanced manifest version or HEAD. Use a manually dispatched workflow on a GitHub-hosted runner, a `release` environment restricted to the default branch, `contents: write` and `id-token: write`, and no stored npm tokens or `NODE_AUTH_TOKEN`. Verify current tool compatibility and actual npm JSON shapes, especially pack/view output differences between npm 11 and 12.

npm publication and registry visibility are separate events: delayed confirmation must not block GitHub Release creation or next-development preparation. Retry fresh registry lookups with bounded waits only for missing-version visibility; on timeout, persist “release could not be verified” without failing or republishing. Authentication, network, malformed metadata, version mismatch, and integrity mismatch remain failures. Make phases visibly observable and persist verification results and GitHub job summaries; release-it hides successful hook output, so do not rely solely on hook stdout. Retain hidden recovery artifacts with `include-hidden-files: true`, and isolate `GITHUB_STEP_SUMMARY` in simulated-release tests. Recovery must inspect registry state, remote refs, GitHub Releases, and retained artifacts before retrying, completing only missing steps without duplicating publication or moving tags. Document verification limits and recovery in RELEASING. Example: [release recovery and verification ordering](https://github.com/dblock/eslint-plugin-prose-spellcheck/pull/9).

For both JavaScript and Ruby trusted-publishing flows, configure the `release` environment for the default branch without required reviewers or deployment approval gates unless the user explicitly requests them. Release workflows must push release metadata and the next development version directly to `master`, not open PRs for those updates. When authorized to set up either flow, remove any ruleset or classic protection requirement for PRs that blocks it, retaining active force-push and branch-deletion protections with no bypass actors. Verify effective rules and document in AGENTS, CONTRIBUTING, and RELEASING that removing the PR requirement permits direct pushes by all writers, not only the workflow; ordinary development still follows the project's PR convention. Release setup authorization covers these necessary protection changes, not release dispatch, publication, or tags.

With authorization, configure the npm GitHub Actions trusted publisher for the actual owner/repository, `release.yml`, and environment `release`, enabling direct publication rather than stage-only. Use current `npm trust github`/`npm trust list` support (npm 11.15+) or the npm website; ask the user to complete browser 2FA when needed, never request codes or tokens in chat. Read back saved settings; configuration alone does not prove OIDC publication, and a new publisher must publish successfully within two days or expire (verify current npm policy). Apply the authorized release-setup protection policy above; never reuse another repository's authorization or weaken force-push/deletion protections. Update RELEASING with verified setup, manual dispatch, provenance, recovery, and verification limits. Run tests/lint before pushing, add a concise changelog entry, and pause after opening the PR; do not merge, dispatch, publish, or tag without authorization. References: [release automation](https://github.com/dblock/eslint-plugin-markdown-preferences-paragraph/pull/7), [version handling](https://github.com/dblock/eslint-plugin-markdown-preferences-paragraph/pull/8), and [verified publisher setup](https://github.com/dblock/eslint-plugin-markdown-preferences-paragraph/pull/13).

For Ruby projects, configure releases with [ruby-gem-release](https://github.com/dblock/ruby-gem-release): verify its current stable release and compatibility, add it as a development dependency, install its standard Rake tasks with the project's version and changelog formats, and add a manually dispatched `release.yml` calling its reusable workflow at the corresponding release tag. Follow its current sample and documentation for workflow inputs, permissions, and dry runs; document the `release` environment and RubyGems Trusted Publishing setup in RELEASING. Apply the shared authorized release-setup protection policy above. Verify setup without publishing; credentials, trusted-publisher setup, release commits/tags, and release dispatch still require explicit authorization.


## 6. Configure CI

Create the shared separate Test, Lint, and Package workflows with explicit `matrix.entry` combinations, least-privilege permissions, caching, and relevant compatibility coverage. Add coverage with Coveralls. Record the CI conventions and the distinction between local validation and PR-only Danger checks in AGENTS and CONTRIBUTING.

For Ruby projects, add Danger with `danger-pr-comment` and `danger-changelog` to development dependencies, configure a Dangerfile, and run Danger in PR CI with permissions needed for PR comments; verify each gem name resolves on RubyGems before installing. Keep changelog checks consistent with the project's exact changelog format: `danger-changelog`'s default Intridea placeholder is `* Your contribution here.`, and setting a dash placeholder may be normalized into an invalid `* - Your contribution here.` line. When the project requires a dash-style placeholder, do not call `changelog.check!` with that incompatible default parser; use a compatible changelog format or run only the update reminder, and state clearly which checks are enabled. Danger 9.6.1 fails to load with `git` 6.0.0 (`uninitialized constant Git::Base`); verify whether the upstream fix is available, and only while it is unresolved constrain `git` to `< 6`. For JavaScript projects, add Danger only when requested.

## 7. Validate and open the implementation PR

Once implementation is ready, apply the shared final-validation policy before committing and opening its PR.

Build the gem with `bundle exec rake build` or create an npm tarball with `npm pack`, then perform the shared real-artifact consumer validation. Examples: [exact-archive validation and release procedure](https://github.com/dblock/eslint-plugin-portable-paths/pull/9) and [empty-archive override regression and recovery](https://github.com/dblock/eslint-plugin-markdown-preferences-paragraph/pull/18).

Commit the validated implementation and open its PR using the shared branch, attribution, and verification rules; pause for the required review.

## 8. Refine documentation linting

Documentation linting is configured in the scaffold for both ecosystems; refine it as implementation adds documentation, using a focused follow-up PR when needed. Apply the shared documentation-linting policy. Check embedded Ruby with `rubocop-md` and embedded JavaScript with ESLint's Markdown processor. Use ESLint for all JavaScript project documentation checks.

Validate affected checks before committing and opening the follow-up PR.

## 9. Create a logo in a follow-up PR

Propose 3–5 distinct, creative logo concepts reflecting the project's purpose and show quick, clearly labeled visual previews before asking the user to choose one. Prefer a comparison sheet with consistent scale and presentation; do not require a choice based on text descriptions alone. Obtain any required image-generation authorization before rendering. Keep draft previews in session artifacts rather than committing unselected concepts.

Iterate on previews with the user before committing to a direction. When refining a chosen preview, use it as the reference and preserve its composition except for the requested changes. Obtain explicit approval of the selected preview before finalizing artwork or opening the logo PR.

Save approved assets under `assets/` and retain editable sources when available. Put the logo first in README, followed by the project title, badges, and description, with blank lines between blocks; use an `<img>` with descriptive alt text and an explicit display width (160 pixels by default), as in [rubocop-prose's README](https://github.com/dblock/rubocop-prose/blob/main/README.md). Preserve upstream artwork and license notices when adapting existing assets; document provenance and regeneration instructions in DESIGN. Inspect both the full-size asset and README rendering for legibility and clipping. Examples: [RuboCop-inspired scroll](https://github.com/dblock/rubocop-prose/pull/60) and [portable-paths folder logo](https://github.com/dblock/eslint-plugin-portable-paths/pull/8).
